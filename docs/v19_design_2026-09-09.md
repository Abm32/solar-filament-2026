# V19 design — a different detector family (Mask2Former), not another YOLO-seg variant

> Status: DESIGN, not yet run. Written 2026-09-09 while an Azure NCASv3_T4 quota
> increase (64→96 vCPUs, ticket `solar-filament-t4-quota-202609091912`) is pending,
> so training can start the moment GPU capacity is available.

## Why this and not another YOLO-seg lever

`RESUME_TOMORROW.md` (2026-09-09) and `ceiling_analysis_2026-09-07.md` establish,
with measurements, that every remaining YOLO-seg-family lever is closed:

- Raw proposal IoU is capped at **0.8734** by YOLO's 256×256 (1/4 of `imgsz=1024`)
  mask-prototype layer, upsampled 8x to 2048×2048. `mask_ratio=1` (E026/E027) moved
  this ceiling to 0.9119/0.9093 across two seeds but produced **zero public score
  movement** when composed with the best inference recipe (V17, still 0.39).
- **212 of 1134 GT instances (18.7%) are missed by every one of six proposal
  populations on disk** (V6, arm_r1/r2 seed1/seed2, at box iou 0.7/0.3) — a
  detection-family-level blind spot, not a threshold or ensemble problem. The
  oracle union recall is 0.8131; the oracle union PQ is only 0.5849 at zero FP
  (E028), still below the corrected target.
- Three independent attempts at a higher-capacity FN-weighted mask head *bolted
  onto YOLO's proposals* (V11 refiner family, V14 dual IoU head, V15 mask head)
  all failed, because the refiner/head can only work within a mask envelope YOLO's
  own coarse prototypes already truncated.
- The corrected local→public transfer model (E027,
  `scripts/analyze_public_transfer.py`) says local PQ needs to reach **≥0.6269**
  for public 0.55, not the previously-assumed 0.60. Local is currently 0.4487.

Every closed lever shares one root cause: **the mask comes from a
coarse-resolution CNN prototype layer, and the recall ceiling comes from a single
detector family's inductive bias (grid-anchor-based YOLO proposals).** The doc's
own conclusion (`RESUME_TOMORROW.md`, "What would change this") is explicit: *only
a genuinely different detector, and it needs hardware we do not have, or a
different architecture family.* This design is that different architecture
family, now that a T4-class GPU (via Azure, once quota clears) removes the "we do
not have the hardware" half of that sentence for a reasonably sized model.

## Architecture choice: Mask2Former (ResNet-50 or Swin-T backbone)

Candidates considered:

| architecture | mask resolution | recall mechanism | verdict |
| --- | --- | --- | --- |
| YOLO-seg (current) | 1/4 `imgsz` prototype, upsampled | grid/anchor proposals | closed, see above |
| Cascade Mask R-CNN | RoIAlign at fixed crop res (e.g. 28x28 → upsampled per-instance) | two-stage RPN + cascade refinement | better recall via RPN recall tuning, mask res still crop-bounded |
| **Mask2Former** | **per-pixel query decoding at full feature-map resolution, no RoI crop** | **set-prediction (bipartite matching), no anchor/grid prior** | **selected** — attacks both walls: no coarse-crop mask ceiling, no anchor-density recall ceiling |

Mask2Former (Cheng et al., 2022) decodes each of a fixed number of learned object
queries against multi-scale pixel-embedding maps via masked attention, producing
per-instance masks without proposal cropping. Two properties matter here
specifically:

1. **No RoI-crop mask ceiling.** YOLO's ceiling (0.8734, later 0.9119) comes from
   decoding a mask from a small fixed-resolution feature grid. Mask2Former's mask
   head operates on the full per-pixel embedding map (stride 4 relative to input,
   i.e. 512x512 embeddings at 2048 input — 4x the linear resolution of YOLO's
   256x256 protos at `imgsz=1024`), which is the direct lever the ceiling analysis
   says is required ("own the mask... more capacity than a ResNet18 U-Net at
   256px").
2. **No anchor-density recall ceiling.** Set prediction with a fixed, generous
   query budget (100-200 queries, tunable) does not depend on an anchor grid
   matching thin, elongated filament shapes. The 18.7%-missed-by-everyone
   instances are disproportionately small/elongated (§6 of ceiling_analysis); this
   is exactly the population anchor-based detectors structurally under-serve.

## Practical plan (T4-feasible, learned from V18's failure)

V18's OOM (native `imgsz=2048`, `mask_ratio=1`, T4, 14.56 GiB) is the load-bearing
lesson here: **do not scale image resolution or per-image instance capacity past
what a single T4 holds, and probe the worst case, not a subsample.** Concretely:

- Train at **1024×1024** input (matching the current pipeline's `imgsz`, so
  raw-proposal comparisons stay apples-to-apples against the existing 0.7989
  detector-stage recall baseline), with **full-resolution sliding-window
  inference at 2048×2048** at test time (Mask2Former supports this; it is a
  segmentation-map decode, not a crop-classifier).
- **ResNet-50 backbone**, not Swin — smaller memory footprint, faster iteration,
  and this dataset (707 train images) does not have the scale to benefit from a
  larger transformer backbone; if ResNet-50 clears the SUBMIT_BAR, Swin-T is the
  natural V20 follow-up, not a first attempt.
- **Batch size 2, gradient accumulation 4** (effective batch 8) — conservative
  starting point given the T4's 14.56 GiB budget and this project's own memory
  lesson; validated with a smoke run at full instance density (the image with the
  most annotated filaments, not a random subsample) before committing to a full
  run, exactly the fix V18's post-mortem prescribes.
- **100 object queries** — 1134 GT instances / 707 train images ≈ 1.6 mean
  instances/image, but the max-density image drives memory; checked at smoke time.
- Loss: standard Mask2Former composite (classification + mask BCE + mask dice),
  **not** yet the Focal-Tversky loss ceiling_analysis recommends for the YOLO
  refiner — that recommendation was scoped to a head bolted onto YOLO's crops;
  revisit only if Mask2Former's own dice term underperforms on the small-instance
  band (§6's 338 smallest-30%-by-area instances) after a first full run.

## Predeclared protocol (same discipline as V11–V18)

- **Frozen control baseline for comparison**: the accepted V17 submission
  (`56103401`, public 0.39, tune 0.448703) and its full candidate grid in
  `outputs/kaggle_v17_cache_pull/`. V19 does not need to reproduce a byte-identical
  CSV (there is no shared artifact to reproduce — this is a new detector, not a
  rerun of an existing one), but it must reproduce **the same tune/audit split**
  used throughout this project so PQ numbers are comparable.
- **SUBMIT_BAR** (authorizes exporting a CSV at all): tune PQ >= V17's 0.448703
  AND audit PQ >= its corresponding audit figure. Anything below this is a
  training-diagnostics-only result, not a submission candidate.
- **PROMOTION_GATE** (authorizes calling this a real architectural gain, worth a
  Kaggle submission): tune PQ >= 0.55 (roughly the local level the corrected
  transfer model says is needed for a meaningfully different public score, given
  a ∈ [0.01, 0.87] and the observed data) — a large, unambiguous jump, not a
  +0.01 increment, precisely because E024 showed +0.003–0.010 gains do not move
  the public score at all under the current (falsified-offset) uncertainty.
- **Recall and mean-IoU are reported separately at every checkpoint**, mirroring
  ceiling_analysis §2's two-axis framing, so a failure mode is diagnosable (e.g.
  "recall improved but IoU didn't" vs "neither moved") rather than only a single
  scalar PQ.
- **Smoke test before full run**: run on the max-instance-density image plus a
  20-image subsample AT FULL RESOLUTION density check (not a random-fraction probe
  — this is the exact V18 lesson), verify peak GPU memory, then launch full
  training only after the smoke run's peak memory has headroom under 14.56 GiB.

## What happens if this also fails to clear PROMOTION_GATE

If Mask2Former reaches SUBMIT_BAR but not PROMOTION_GATE, it still directly tests
the doc's own falsifiable claim ("only a genuinely different architecture family
could change this") and should be submitted once regardless of the gate, purely
to get a second real data point on the local→public transfer function — the
project currently has exactly one detector family's worth of transfer data (5
points, all YOLO-seg), and a second family's point materially improves
`analyze_public_transfer.py`'s feasible-slope estimate even if the PQ itself is
unremarkable.
