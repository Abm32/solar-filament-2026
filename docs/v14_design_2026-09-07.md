# V14 design — attack both PQ axes in one run

Written **before** the run, 7 September 2026. Rationale and arithmetic in
[`ceiling_analysis_2026-09-07.md`](ceiling_analysis_2026-09-07.md).

## Why this run exists

Three submissions score 0.39. The ceiling analysis shows why: reaching public 0.55
needs local tune PQ ≈ 0.60, and that requires **recall ≥ 0.85 together with mean
matched IoU ≥ 0.75**. Every experiment so far moved one axis by ~0.005.

Current: recall **0.6049**, mean matched IoU **0.6855**, FP 309, PQ 0.4418.

Two measured pools, both untouched:

| pool | size | why it is stuck |
| --- | ---: | --- |
| grouped proposals killed by the fixed 0.40 cutoff | **278** | detector confidence is a poor proxy for mask quality (E021 bounded only the *cheap-feature* fix) |
| GT with support >0.5 but raw mask IoU ≤0.5 | **84** | the object is found; the *mask* fails |

And one measured non-lever: `refined_free` ≈ `refined_constrained`, so removing the
proposal clamp is worth ~0 by itself. The head and its objective must change.

## Architecture: two heads on one shared encoder

```
crop (3ch grayscale + 1ch proposal hint) 256x256
        │
   ResNet34 encoder  (V6/V11 used ResNet18)
        │
   ├── mask head    -> 256x256 logits   (deep supervision at 1/2, 1/4)
   └── IoU head     -> scalar in [0,1]  (predicted IoU of its own mask vs GT)
```

Both heads train together. The mask head attacks the IoU axis; the IoU head
attacks the recall axis by replacing the fixed 0.40 confidence cutoff with a
learned mask-quality estimate. Sharing the encoder is what makes this one run
instead of two, and it is also why the IoU head can see mask evidence — the thing
E021 proved summary geometry features cannot supply.

### Arm A vs Arm B (the controlled comparison)

| | encoder | mask loss | IoU head | selection score |
| --- | --- | --- | --- | --- |
| **control** | frozen V11 `proposal_centered_e4` | — | — | detector confidence, fixed 0.40 |
| **arm_a** | ResNet34, warm-started | 0.5 BCE + 0.5 Dice (as V11) | yes | learned IoU |
| **arm_b** | ResNet34, warm-started | **Focal-Tversky β=0.7 α=0.3** + 0.5 BCE | yes | learned IoU |

Arm B isolates the FN-weighted loss, which the bottleneck decomposition
specifically motivates: smallest-30% instances sit at mean raw IoU 0.518, barely
over the 0.5 matching bar, so eroding them one pixel flips TP→FN.

Only the loss differs between A and B. Everything else — cohort, sample order,
epochs, LR schedule, augmentation, seed — is identical and asserted at runtime.

## Training

- **Cohort:** reuse V11's proven `build_training_cohort` matching policy
  (min_iou 0.30, max_second 0.20, min_margin 0.15) over the same 566 training
  files. Cohort hash pinned; arms must consume identical sample orders.
- **Warm start:** V11 `proposal_centered_e4` weights where shapes match
  (ResNet18→ResNet34 differs, so the encoder is ImageNet-init and the decoder is
  fresh; documented rather than silently partial).
- 8 epochs, AdamW lr 1e-4 → cosine, weight decay 1e-4, FP32, batch 16, seed 42.
- **IoU-head target:** the actual IoU between the arm's *own* predicted mask
  (thresholded at 0.5) and the GT crop, recomputed per batch. Loss: MSE on the
  IoU scalar, weighted 0.2 so it never dominates the mask objective.
  Detached from the mask branch so IoU supervision cannot degrade mask gradients.

## Inference and selection

For each proposal the model emits a mask and a predicted IoU. Two knobs replace
the single confidence cutoff:

- `mask_threshold` ∈ {0.40, 0.45, 0.50} — binarisation of the mask logits
- `iou_gate` ∈ {0.20, 0.25, 0.30, 0.35, 0.40, 0.45, 0.50} — minimum *predicted*
  IoU to keep an instance

3 × 7 = **21 predeclared candidates per arm**, enumerated up front. Selection is
tune-PQ only; audit never selects.

Ranking by predicted IoU rather than detector confidence is the mechanism aimed at
the 278-instance pool: a proposal with mediocre detector confidence but a clean
mask should now survive, and a confident proposal with a bad mask should not.

## Gates, declared before any V14 number is observed

- **SUBMIT_BAR** (authorises exporting a CSV at all): tune PQ ≥ **0.4418**
  (V13, the best measured candidate) **and** audit ≥ **0.4501** (E015 floor).
  Clearing this authorises *measurement*, not promotion.
- **PROMOTION_GATE:** tune ≥ V13 + **0.010** with audit ≥ V13's audit. The margin
  is deliberately 10× the V13 delta because V13 proved that +0.004 local is
  invisible on a two-decimal public score. **Do not spend a submission on less.**
- **Frozen control first.** The control arm reproduces E015's exact tune/audit
  counts and its exported CSV must hash to
  `bf11690e9bcce73b0c627096cc1198d9fb0916650f7fa4b3f08f1167bb76bde9`. If that
  fails the run aborts before any claim, as in V12/V13/E-A.

## Diagnostics this run must report

Because the target requires both axes, the report separates them explicitly:

- recall, mean matched IoU, and FP **as three separate numbers** per candidate
  (previous runs reported only aggregate PQ, which hid which axis moved)
- IoU-head calibration: predicted vs actual IoU, and its AUC for ranking
  TP-vs-FP — directly comparable to E021's `consensus_score` AUC of **0.7252**
- how many of the 278 cutoff-pool and 84 mask-pool instances were recovered
- per-area-decile recall, to confirm whether Focal-Tversky helped small instances

## Honest expectation

Mechanically available without a detector retrain: recall ≈ 0.836 (raw-proposal
0.799 plus half the mask-recoverable pool), so

| | IoU 0.72 | 0.75 | 0.78 |
| --- | ---: | ---: | ---: |
| recall 0.836, FP 309 | 0.5709 | 0.5947 | 0.6185 |
| recall 0.836, FP 200 | 0.5982 | 0.6231 | 0.6481 |

→ local **0.57–0.62**, public **≈0.52–0.57**. First plan whose arithmetic reaches
the target rather than hoping.

Risks, stated up front:

1. The IoU head may not beat detector confidence at ranking. E021's linear probe
   failed at this; the difference here is that this head reads mask pixels. If its
   AUC lands near 0.7252, the recall axis does not move and the run is a partial.
2. Loosening the gate to admit the 278 pool can add FP faster than TP — the same
   trade that killed the naive threshold drop and E022's 1536 inference. The
   `iou_gate` sweep prices this rather than assuming it.
3. Mean IoU may not reach 0.72. The raw proposals cap at 0.873, and the refiner
   currently achieves 0.686; 0.72–0.78 is between those, so it is not obviously
   out of reach, but it is the single least certain number in this plan.

If V14 clears SUBMIT_BAR but not PROMOTION_GATE, the correct action is to **record
it and not submit** — V13 already established that a small local gain buys nothing
public. The next step in that case is a detector retrain with `mask_ratio=1`, which
raises the 0.873 proposal cap itself.
